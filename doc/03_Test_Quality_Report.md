# 테스트 실효성 점검 보고서

"테스트가 통과한다"와 "테스트가 결함을 잡는다"는 다르다. 이 문서는 현재 테스트가 실제로 결함을 잡는지 **측정**한 결과와, 그 결과로 보강한 내용, 재현 방법, 남은 일을 기록한다. (측정 시점: 2026-10-30, 엔진 기준 커밋 `441ef82` 이후 작업 트리)

## 1. 방법
1. **뮤테이션 테스트(C++ 엔진)**: 소스의 연산자를 하나씩 바꾼 변이(`<`->`<=`, `==`->`!=`, `&&`->`||`, `+`<->`-`, `*`->`/`, `true`<->`false`)를 만들고, 빌드 후 `engine_tests`를 돌려 **실패하면 killed(테스트가 잡음), 통과하면 survived(테스트가 못 잡음)**로 센다. 컴파일이 안 되는 변이는 invalid로 제외한다. 별도 복제본 4개에 샤드로 나눠 병렬 실행했다.
2. **코드 커버리지(C#)**: `coverlet`(이미 참조됨)로 `GunGame.Interop.Tests`와 `GunGameEditor.UiTests`의 라인 커버리지를 합집합으로 측정.
3. **손으로 하는 결함 주입**: 새 기능마다 핵심 연산을 일부러 망가뜨려 해당 테스트가 실패하는지 확인(이번 세션 내내 수행).
4. **정적 점검**: 단언이 없는 테스트, 조건이 안 맞으면 조용히 건너뛰는 테스트, 항상 참인 단언을 스크립트로 검색.

## 4. 남은 생존 변이의 분류 (대부분 동등 변이)
남은 C++ 생존 변이 약 90개를 읽어 보면 다음처럼 분류된다. 이 변이들은 관측 가능한 동작을 바꾸지 않거나 다른 검사가 같은 결과를 내므로 테스트로 잡을 수 없거나 잡을 가치가 낮다.
- **경계에서 부동소수 `==`/`<=`**: 오차 허용(`kEpsilon`), 정확히 겹친 접촉(`>=` vs `>`), `t < 0` vs `t <= 0`처럼 경계 값이 같은 결과를 내는 곳.
- **다른 검사가 같은 결과를 내는 방어 코드**: 렌더러 인자 검증 일부(0 크기는 D3D 생성이 어차피 실패), 스켈레톤 본 수 검증(C API가 먼저 거부), `eye==target`(수직 검사가 같은 결과) 등.
- **루프 상한 `<` -> `<=`**: 배열 범위를 넘는 정의되지 않은 동작이라 테스트할 수 없음.
- **상태 플래그 정리**: `_hasCutDirection = false`의 `true` 변이(다음 프레임에 같은 분기가 다시 정리).
- **수렴 속도만 바꾸는 변이**: 충돌의 `return true/false`, `moved = false` 초기화(결과는 같고 반복 횟수만 변함).
- **8비트 양자화와 UNORM 변환이 같은 값**: 배경색 `colorBits < 8` 경계.
- **`polygon.cpp` 교차 검사의 `||` 결합 순서 일부**: 한 꼭짓점이 두 변에 속해 어느 쪽 역할로도 잡히므로 한쪽을 막아도 다른 쪽이 잡는다.
확실히 하려면 개별 변이를 하나씩 재확인해야 한다(아래 5절 주의).

## 5. 재현 방법 (`tools/mutation/`)
- `mut_cpp.py <복제본> <샤드> <샤드수> <출력.json> <파일1,파일2,...>`: C++ 뮤테이션. 복제본은 저장소를 `git clone`하고 `cmake -S . -B build -A x64`로 빌드해 둔 것이며 **샤드마다 별도 복제본**이어야 한다(빌드 폴더와 임시 폴더를 공유하면 서로 간섭). 각 샤드는 `TMP/TEMP`를 복제본 안의 폴더로 바꿔 임시 파일 충돌을 막는다. 속도는 변이당 약 15~25초.
- `mut_cs.py <복제본> <샤드> <샤드수> <출력.json> <테스트 프로젝트> <파일1,...>`: C# 뮤테이션(`dotnet test`). 복제본의 `build\bin\gge.dll`이 필요하다. 2026-10-31에 실행했다(7절).
- `cov_report.py <결과 폴더>`: `<결과 폴더>\cov_interop`, `cov_ui`에 `dotnet test --collect:"XPlat Code Coverage" --results-directory ...` 결과를 두고 실행하면 파일별 라인 커버리지와 미커버 줄을 출력.
- **주의(중요)**: 일괄 실행에서 증분 빌드/타이밍 때문에 **거짓 생존**이 나올 수 있다(UI 변이 1건이 일괄에서는 생존, 단독 5회 반복에서는 매번 killed). **killed는 믿어도 되지만 survived는 개별로 다시 돌려 확인**한 뒤에만 "테스트 구멍"으로 판단한다. 특정 줄의 변이만 다시 돌리려면 `mut_lines.py <복제본> <파일> <줄,줄,...>`(해당 줄의 연산자 변이를 순서대로 적용/복원)을, 결과 비교는 `mut_compare.py`(1차/2차 JSON 비교, 생존 목록 출력)를 쓴다.
- 모든 스크립트는 변이를 적용한 뒤 `finally`에서 원본을 복원한다. 중단되었다면 복제본에서 `git checkout -- .`로 되돌린다.

## 6. 이번 점검의 한계 (솔직한 기록)
- (해결됨) C# 뮤테이션은 1차 점검 때 실행하지 못했으나 2026-10-31에 실행했다(7절).
- C++ 2차 측정은 마지막 보강(임의 축 회전, 닿는 변) **이전** 코드로 했고 전체 재측정은 하지 않았다.
- 커버리지는 "실행됨"이지 "검증됨"이 아니다(NUL 경로 테스트가 대표 사례). 뮤테이션과 함께 봐야 한다.
- 엔진 쪽 **독립 기준** 차등 테스트(다각형 포함, 회전 행렬)는 같은 실수를 공유하지 않도록 다른 알고리즘으로 짰지만, 기준 자체가 틀릴 가능성은 0이 아니다(수식으로 교차 확인함).
- 키보드 입력 매핑, 파일 대화상자, 트리 끌기 시작, `SelfTest`는 xUnit으로 검증하지 못한다.
- 렌더링은 WARP 기준으로만 검증했다(하드웨어 GPU 결과와 다를 수 있음). 골든 이미지는 같은 환경에서 재생성한 것이다.

### 간헐 실패 원인 규명 (UI 테스트)
유휴 상태에서도 약 1/3 확률로 `PlayAndStop...`/`OrbitDragIsIgnoredWhilePlaying`이 실패했다. 실패 시 두 이미지를 저장해 보니 **캡처한 프레임이 찢어져(가로 줄무늬) 있었다**: `RenderTargetBitmap`으로 `WriteableBitmap`을 다시 그리면 WPF 렌더 스레드가 아직 반영하지 못한 이전 프레임이 섞인다. 제품 버그가 아니라 캡처 방식 문제였고, 뷰포트 캡처를 비트맵 픽셀 직접 복사로 바꾼 뒤 UI 테스트 6회 연속 통과. 부하 탓으로 넘기지 않고 원인을 확인했다.

### 새 기능의 결함 주입 (손으로, 테스트가 실패하는지 확인)

### 새로운 종류의 검증
- **두 구현의 교차 검증**: C# 플레이 모드(`PlaySession` + `SceneSync`)와 C++ 런타임을 같은 입력 대본(약 420프레임)으로 돌려 프레임마다 위치/방향/방/트리거 이벤트가 같은지, 조명·알파·그림자·텍스처·애니메이션이 든 장면의 화면이 6개 시점에서 **바이트 단위로 같은지** 비교한다.
- **문서 기준 독립 작성기**: C++ 테스트의 `.ggs` 작성기는 형식 주석만 보고 C# 베이커와 별개로 짰다. 두 구현이 "서로 합의"하는 것이 아니라 문서와 일치하는지 본다.
- **손상 파일 퍼징**: 체크섬을 다시 맞춘 무작위 손상 400건에서 로더가 죽거나 멈추지 않고(정상 로드 또는 사유 있는 오류) 거부 비율이 충분한지 확인.
- **플레이어 종단 검증**: 헤드리스 `gge_player.exe`가 만든 화면이 엔진 테스트의 골든과 바이트까지 같다(ctest).
