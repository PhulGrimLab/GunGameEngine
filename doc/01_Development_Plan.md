# GunGameEngine 개발 계획

## 목표
SIGNALIS 스타일(PS1풍 저해상도 3D, 고정 카메라, 3인칭 탐험/전투/퍼즐)의 게임을 만드는 C++ 엔진과 C#/WPF 개발 툴.

## 기술 결정
| 항목 | 결정 | 이유 |
|---|---|---|
| 렌더러 | D3D11, 저해상도 오프스크린 렌더 타깃 후 최근접 업스케일 | 텍스처/조명/그림자/스키닝/후처리를 감당하면서 PS1 룩은 후처리로 구현 |
| 툴 표시 | 엔진이 CPU로 읽은 BGRA 프레임을 WPF `WriteableBitmap`에 복사 | 해상도가 낮아 비용이 작고 D3DImage 연동이 필요 없음 |
| C++ ↔ C# | `extern "C"` API + P/Invoke (`engine/include/gge/gge.h`) | C++/CLI보다 단순, 컴파일러 버전에 덜 묶임 |
| 좌표계 | 오른손, Y-up, 앞면 CCW | 문서로 고정 |
| 카메라 | 고정 카메라가 1급 개념 (방마다 앵글 배치) | 목표 게임 장르 |
| 스크립트 | C#, .NET 호스팅은 후순위 | 큰 별도 과제 |

## 결정 기록
- **런타임 씬 로더 = (b) 에디터가 바이너리 씬으로 굽기**(결정됨, 7+단계에서 구현): 씬 JSON은 C#만 읽고, 독립 플레이어는 구운 `.ggs`만 읽는다. C++에 JSON/OBJ/glTF 파서를 두지 않으며, 굽는 쪽(C# `SceneBaker`)이 이미 있는 C# 임포터를 그대로 재사용한다. 자세한 규약은 아래 "구운 씬과 독립 플레이어".
- **열린 결정**: 선택 하이라이트, 기즈모(뷰포트에서 직접 이동/회전)는 아직 없다.

## 스켈레탈 애니메이션 규약
- **엔진은 시간 상태가 없다.** 호출자가 `gge_object_set_pose(clipA, timeA, clipB, timeB, blend)`로 매 프레임 포즈를 지정하고, 반복/속도/크로스페이드는 C# `AnimationPlayer`가 관리한다(런타임 플레이어 단계에서 C++로 옮길 수 있음).
- 본은 부모가 자식보다 앞에 오도록 정렬(임포터가 재정렬). 역바인드 행렬은 행 벡터 규약이며 glTF의 열 우선 배열과 메모리 배치가 같아 변환 없이 쓴다.
- 포즈(본 전역 행렬)는 모델 공간이라 오브젝트 변환과 독립이다. `gge_object_get_pose`로 조회해 검증/디버깅에 쓴다.
- **glTF 지원 범위**: 삼각형, POSITION/NORMAL/TEXCOORD_0/JOINTS_0/WEIGHTS_0, 스킨 1개, translation/rotation/scale 선형 채널. STEP/CUBICSPLINE·sparse는 오류, 아르마추어 노드 변환은 무시(경고), 재질/텍스처는 무시(노드가 따로 지정).
- 알려진 한계: 클립 재생 중 구조 변경(Rebuild)은 재생 시간을 유지하지만 크로스페이드 상태는 유지하지 않는다. 시간 슬라이더(스크럽)와 본 시각화는 아직 없다.

## 게임플레이 월드 규약 (6단계)
- **`GgeWorld`는 렌더러와 독립**이다(`engine/src/world.*`, `collision.*`). 로직은 모두 바닥(XZ) 평면 기준이고 Y는 보지 않는다.
- **방**: 단순 다각형(오목 가능, 감김 방향 무관, 경계 포함) + 고정 카메라. 활성 방은 현재 방이 점을 포함하는 한 유지(겹침 경계 깜빡임 방지), 어떤 방에도 없으면 마지막 방 유지. 같은 점이 여러 방에 속하면 ID가 작은 방이 앞선다.
- **충돌**: 정적 AABB 콜라이더 + 원형 이동체. `gge_world_move_circle`이 이동량을 radius/2 이하 걸음으로 쪼개 걸음마다 밀어내므로 벽 슬라이딩이 되고 얇은 벽을 통과하지 않는다. 틈이 지름보다 좁으면 두 모서리에 끼어 멈춘다. 이동량이 radius/2의 1024배를 넘으면 거부한다.
- **입력(카메라 상대 이동)**: 엔진은 정규화 축(-1..1)만 받는다(키보드/게임패드 읽기는 호출자). `gge_world_move_input`이 활성 방 카메라 시선의 수평 성분을 "앞", 앞 x 위를 "오른쪽"으로 해 월드 이동량으로 바꾼다. 크기는 1로 제한하고, 데드존(0.2) 이하는 0, 그 위는 `(크기-0.2)/0.8`로 0부터 늘어난다(천천히 걷기 가능). 호출자는 **매 프레임** 호출해야 한다(입력 없음 프레임이 방향 기준 갱신 시점이다). 결과를 `gge_world_move_circle`에 넘기면 충돌이 반영된다. 시선이 거의 수직인 카메라(수평/전체 길이 비율 1e-3 이하)는 방 등록에서 거부한다.
- **카메라 컷**: 입력을 누른 채 방이 바뀌면 방향 기준은 입력을 시작한 방 카메라를 유지한다(컷 직후 캐릭터가 되돌아가는 것 방지). 입력을 놓거나, 컷 직후 입력 방향에서 60도 넘게 꺾으면 현재 방 기준으로 갱신한다. 입력이 끊기지 않는 채 장면이 바뀌는 텔레포트/컷신에는 `gge_world_reset_input_frame`을 호출한다. 탱크 컨트롤 모드와 캐릭터 회전(facing)은 아직 없다.
- **트리거**: 방과 같은 규칙의 XZ 평면 다각형 영역(`polygon.*`을 방과 공유: 오목 가능, 경계 포함) + 호출자 정의 `tag`(문/아이템 연결용). `gge_world_update_triggers(x, z)`를 프레임마다 부르면 상태가 바뀐 트리거의 Enter/Exit 이벤트가 큐에 쌓이고 `gge_world_poll_trigger_event`로 꺼낸다. 한 갱신 안에서는 Exit가 먼저, 그다음 Enter이며 각각 트리거 ID 순(A에서 나와 B로 들어가면 Exit A, Enter B). 처음부터 안에 있으면 Enter. 꺼진 트리거는 "밖"으로 취급해, 안에서 끄면 Exit, 안에서 다시 켜면 Enter가 생긴다. 큐는 1024개까지이며 가득 차면 가장 오래된 것부터 버린다(매 프레임 폴링해야 한다). 위치를 프레임마다 샘플링하므로 한 프레임 이동 거리보다 얇은 영역은 건너뛸 수 있다. 플레이어 한 명만 추적한다(여러 개체는 아직 없음).
- 한계: 회전 상자/캡슐 높이/동적 충돌체/방 폴리곤을 벽으로 쓰는 것은 아직 없다. 충돌체는 월드 상태(활성 방)와 무관하게 전역이다.

## 플레이 모드 (에디터)
- **데이터**: 씬 파일(JSON, 버전 1)의 선택 섹션 `gameplay`에 방(`rooms`: 이름, `polygon`=(x,z) 쌍, `camera`={eye,target,fov}), 충돌체(`colliders`: `min`/`max`=(x,z)), 트리거(`triggers`: `polygon`, `tag`), 플레이어(`player`: `node`=루트 노드 이름, `spawn`, `radius`, `speed`)를 둔다. 없으면 이전 파일과 같다(버전 변경 없음). 저장할 때 비어 있으면 쓰지 않는다. 예: `assets/samples/play.scene.json`.
- **편집 UI**: 두 번째 툴바 줄의 **Add Room / Add Collider / Add Trigger / Add Light / Set Player / Delete Item**과 왼쪽 아래 게임플레이 목록, 오른쪽 `GameplayInspector`로 편집한다(순수 로직은 `GameplayEditing`).
  - 새 항목은 편집 카메라가 보는 점(목표점) 주변에 기본 크기로 생긴다: 방 = 8x6 사각형 + 현재 뷰 카메라, 충돌체 = 1x1, 트리거 = 2x2(태그는 최댓값+1). **Use view camera**가 방 카메라를 현재 뷰로 덮어쓴다.
  - 다각형은 줄마다 `x, z`인 텍스트(여러 줄 칸, 포커스를 잃을 때 반영), 숫자는 쉼표/공백 구분. 잘못된 입력(꼭짓점 3개 미만, 숫자 아님, min>=max, 반지름/속도 <= 0, fov 범위 밖 등)은 상태 표시줄에 사유를 보이고 이전 값으로 되돌린다. 충돌체는 최소/최대를 한 칸씩 고치다 뒤집히는 것을 막으려고 뒤집힌 값을 거부하며, 옮길 때는 **Move area by (dx, dz)**를 쓴다.
  - **Set Player**는 계층에서 고른 **루트** 노드를 플레이어로 지정하고 스폰을 그 노드의 (x, z)로 둔다(자식 노드는 거부).
  - 목록 맨 위의 **Lighting: Scene**은 항상 있고 삭제할 수 없다(조명 값 편집, 아래 "조명" 참고). 목록에서 항목을 고르면 게임플레이 인스펙터가, 계층에서 노드를 누르면 노드 인스펙터가 보인다.
  - 툴바의 **Show gameplay**는 방(파랑)/트리거(초록)/충돌체(빨강)/방 카메라 위치(하늘색)/스폰(노랑)을 뷰포트에 가는 선과 표식으로 보여 준다(`GameplayOverlay`). 항목을 추가하면 자동으로 켜진다(점광원 제외).
- **Play/Stop**: Play가 `PlaySession`(WPF 비의존)을 만들고, 타이머(30Hz)가 WASD/방향키를 읽어 `Step(입력, dt)`를 부른다. 한 프레임: 입력 -> 활성 방 카메라 기준 이동량 -> 충돌 이동 -> 활성 방 갱신(카메라 컷) -> 트리거 갱신. 플레이 중에는 활성 방의 고정 카메라로 보고, 마우스 궤도/줌과 씬 편집(툴바, 계층, 인스펙터)은 잠긴다. 트리거 이벤트와 카메라 전환은 상태 표시줄에 뜬다(`PlayLog`).
- **문서는 바뀌지 않는다**: 플레이어의 위치/회전은 `SceneSync.Preview`로 화면(엔진 오브젝트)에만 덮어쓴다. Stop은 `ClearPreview`로 화면을 문서 값으로 되돌린다.
- **규칙/가정**: 플레이어 노드는 루트여야 한다. 플레이어 모델의 앞쪽은 +Z로 가정하고 이동 방향으로 Y 회전을 돌린다. 스폰은 어떤 방 안이어야 한다. 시작할 때 이미 트리거 안이면 첫 Step에 Enter가 온다. 방 카메라가 정해진 것은 시선의 수평 성분이 있는 카메라뿐이다(수직 내려보기 불가).
- **자동 검증 한계**: 키보드 상태(`Keyboard.IsKeyDown`)는 OS 입력이라 UI 테스트에서 만들 수 없어, 타이머가 부르는 `StepPlay`를 직접 호출해 같은 경로를 검증한다. 키 매핑(`ReadPlayInput`) 자체는 자동 테스트가 없다.

## 조명 / 알파 / 그림자 (7단계)
- **밝기**: `앰비언트 + 방향광색 * max(0, N.-L) + sum(점광원색 * max(0, N.l) * a^2)`, `a = saturate(1 - 거리/범위)`(범위에서 정확히 0). 결과는 오브젝트 색 x 텍스처에 곱해지고 그 뒤 PS1 효과(색 깊이/디더)가 적용된다. 색 성분은 유한하고 0 이상(1 초과 과노출은 포화). **기본값(앰비언트 0.25, 방향광 0.75, 방향 (-0.4,-1,-0.6))은 조명 API가 없던 때의 고정 조명과 비트까지 같다**(기존 골든 5개가 그대로 통과).
- **점광원**은 렌더러당 최대 8개(`kMaxPointLights`), ID는 1부터 재사용하지 않는다. 픽셀마다 계산한다(PS1은 정점 조명이지만 이 엔진은 면 단위 노멀을 쓰므로 per-pixel이 더 안정적).
- **알파**: 오브젝트 `alpha`(0..1). 1 = 불투명, 0 = 그리지 않음, 사이 = 알파 블렌딩. 불투명을 모두 그린 뒤 **카메라에서 먼 오브젝트부터** 깊이 쓰기 없이 섞는다(정렬은 **오브젝트 단위**: 한 오브젝트 안의 면끼리, 서로 교차하는 반투명 오브젝트끼리는 정렬하지 않는다). 렌더 타깃의 알파 채널은 항상 255다. 텍스처 알파는 별개로 **컷아웃**(알파 < 0.5(= 127 이하)인 텍셀은 버림, 128은 유지).
- **그림자**: `SetShadow(enabled, planeY, opacity)`로 켜는 **평면 투영 그림자**. `castsShadow`인 오브젝트(스킨 포함, 현재 포즈 그대로)를 방향광 방향으로 `y = planeY` 평면에 눌러 `opacity`만큼 어둡게 칠한다. 깊이/스텐실 버퍼(D24S8)로 겹친 도형도 픽셀당 **한 번만** 어둡게 하고, 앞의 오브젝트에 가려지며, 반투명보다 먼저 그려 그 위에 섞인다.
  - 제약: **바닥 평면 하나에만** 떨어진다(다른 면/벽에는 안 떨어짐), 드리우는 오브젝트는 평면 위에 있어야 한다, 방향광이 아래를 향할 때(y < -0.001)만 그려진다, 점광원은 그림자를 만들지 않는다, 알파가 있는 오브젝트의 그림자도 `opacity` 그대로다.
- **씬 데이터**: 노드의 `alpha`/`castsShadow`와 씬의 `lighting`(`ambient`, `sun{direction,color}`, `points[{name,position,color,range}]`, `shadow{enabled,planeY,opacity}`). 없으면 기본값이며 저장할 때 기본값은 쓰지 않는다(이전 파일과 호환). 점광원 9개 이상, 음수 색, 0 방향, 범위 <= 0, 불투명도/알파 범위 밖은 파일을 열 때 사유와 함께 거부한다. 샘플: `assets/samples/lit.scene.json`.
- **에디터**: 노드 인스펙터의 **Alpha (0-1)**/**Casts shadow**, 게임플레이 목록의 **Lighting: Scene**(앰비언트, 방향광 방향/색, Shadows 체크, 평면 높이, 불투명도)과 **Light: 이름**(점광원, **Add Light**로 목표점 위 2 단위에 생성). 값이 바뀌면 `SceneSync.ApplyLighting()`이 점광원을 모두 지우고 다시 만든다.

## 구운 씬과 독립 플레이어
- **`.ggs`**(구운 씬): 에디터의 **Bake Player Scene...**(`SceneBaker`)가 씬과 그것이 참조하는 모든 것을 하나로 합친다 - 메시는 엔진용 배열(정점/인덱스, 스킨이면 조인트/가중치/스켈레톤/클립)로, 텍스처는 이미지 파일 원본 바이트로, 노드 계층/조명/게임플레이(방, 충돌체, 트리거, 플레이어)와 함께. 같은 경로의 메시/텍스처는 한 번만 넣고, **입력이 같으면 바이트까지 같다**. 형식은 `engine/src/scene_io.cpp` 맨 위 주석이 기준이다(리틀 엔디언, 끝에 CRC-32).
- **굽기 규칙**: 씬에 로드 문제(없는 메시/텍스처 등)가 있으면 거부한다. 없는 클립/플레이어 노드, 자식 플레이어 노드, 방 없음은 사유와 함께 `BakeException`. 파일에 쓰기 전에 **실제 엔진(WARP)에 로드해 한 프레임 진행**해 보고(스폰이 방 밖, 잘못된 다각형 등), 실패하면 쓰지 않으며 기존 파일은 그대로다.
- **엔진 런타임**(`gge_scene_*`, `engine/src/scene.cpp`): `gge_scene_load`가 렌더러에 메시/텍스처/스켈레톤/클립/오브젝트/조명을 만들고 게임플레이 월드를 구성한다. `gge_scene_step`의 프레임 순서는 에디터 플레이 모드와 같다 - 입력 -> 활성 방 카메라 기준 이동 -> 충돌 -> 활성 방 갱신 -> 트리거 -> 애니메이션 -> 플레이어 변환 -> 렌더러 카메라를 활성 방 카메라로. 애니메이션은 에디터의 `AnimationPlayer`와 같은 규칙(시간 0에서 시작, `speed` 배율, 반복, `playing=false`면 0에서 정지)을 이식했고 크로스페이드는 없다(정적 씬이라 클립이 바뀌지 않음). 플레이어가 없는 씬은 애니메이션만 진행한다. 실패한 로드와 `gge_scene_destroy`는 만든 것을 모두 렌더러에서 지운다(씬은 렌더러보다 먼저 파괴). **쓰기 API(스크립트용)**: `gge_scene_set_trigger_enabled(name, enabled)`는 이름이 같은 트리거를 전부 켜고/끄며(없으면 실패, 이름은 대소문자 구분) 이벤트는 다음 `gge_scene_step`에서 나온다(안에서 끄면 Exit, 다시 켜면 Enter). `gge_scene_teleport_player(x, z)`는 플레이어를 즉시 옮기고(방향 유지) 입력 방향 기준을 비운 뒤 활성 방/트리거/카메라/플레이어 변환을 새 위치로 바로 갱신한다(이벤트는 poll로 나오며 Exit가 먼저). 플레이어가 없거나 값이 유한하지 않거나 어떤 방에도 속하지 않으면 실패하고 상태는 그대로이며, 충돌체 안인지는 검사하지 않는다.
- **`gge_player.exe`**(`engine/player/player.cpp`): 엔진 C API만 쓰는 얇은 껍데기. 고정 30Hz 타임스텝(한 번에 최대 5걸음 따라잡기), WASD/방향키 + XInput 왼쪽 스틱(키보드가 눌려 있으면 키보드 우선, 창이 활성일 때만 읽음), Esc 종료, 렌더 해상도 x `--scale` 최근접 확대, 기본 PS1 효과 켬(에디터 기본과 같음, `--no-retro`로 끔), 제목 표시줄에 활성 방과 마지막 트리거 이벤트. 하드웨어 GPU가 기본이고 `--warp`로 소프트웨어 렌더. 헤드리스: `--headless --frames N --keys D:60,W:30 --screenshot out.ppm`은 창 없이 진행하고 결과 한 줄(위치/방향/방/이벤트)을 출력한다. `--self-test`는 입력 매핑과 대본 해석을 검사한다.
- **스크립팅(8단계, `--script`)**: 게임 스크립트는 C# 클래스 라이브러리다. `tools/GunGame.Scripting`(인터페이스만, 엔진 비의존)을 참조해 공개 클래스가 `IGameScript`(`OnStart` / `OnTrigger` / `OnUpdate`, 필요한 것만 구현)를 구현하면 되고 예제는 `tools/GunGame.SampleScripts`다. 실행: `gge_player scene.ggs --script game.dll [--script-type 이름]`(어셈블리의 공개 구현을 타입 이름 순서로 모두 만들고, `--script-type`이 있으면 그 이름(전체/짧은)만). `IScriptContext`로 활성 방/플레이어 위치 읽기, `SetTriggerEnabled`, `TeleportPlayer`, `SetObjectAlpha(노드 이름)`, `Log`(표준 오류에 `[script] ...`)를 쓴다.
  - **구조**: 플레이어(C++, `engine/player/script_host.cpp`)가 hostfxr로 .NET 런타임을 올린다. `hostfxr.dll`은 `DOTNET_ROOT` -> 레지스트리 -> `%ProgramFiles%\dotnet` 순으로 가장 높은 버전을 찾고(nethost 미사용, 헤더 2개는 `engine/third_party/dotnet`), `build\bin\script_host\GunGame.ScriptHost.dll`(기본, `--script-host-dir`로 변경)의 `Entry`가 가진 `[UnmanagedCallersOnly]` 진입점(`Initialize/Start/HandleTrigger/Update/GetLastError/Shutdown`)을 함수 포인터로 받아 부른다. 실제 로직은 일반 클래스 `ScriptRunner`(xUnit으로 검증)에 있고 `Entry`는 얇은 껍데기다. `--script`를 안 주면 .NET은 전혀 로드되지 않는다. 대상 PC에 **.NET 10 런타임**이 필요하다(없으면 사유와 함께 실패).
  - **프레임 규칙**: 시작할 때 `OnStart`(씬 로드 직후, 첫 이벤트 전) -> 이후 고정 걸음마다 `gge_scene_step` -> 쌓인 이벤트를 하나씩 `OnTrigger`로 전달 -> `OnUpdate(1/30)` -> 업데이트가 만든 이벤트 전달. 스크립트가 만든 이벤트(텔레포트 등)도 같은 프레임에 빌 때까지 전달하며, 한 프레임에 1000개를 넘기면(두 트리거로 번갈아 텔레포트 같은 폭주) 사유와 함께 멈춘다. 헤드리스 결과 한 줄의 이벤트에는 스크립트가 만든 것도 포함된다.
  - **오류**: 스크립트를 못 불러오거나(파일 없음, 형식 오류, 스크립트 없음, 필터 불일치, 생성자 예외), 실행 중 예외를 던지면(엔진 API 실패 포함) 사유(`script GunGame.X failed in OnTrigger: InvalidOperationException: ...`)를 표준 오류에 출력하고 종료 코드 1로 끝난다(창 모드는 메시지 상자도). 예외를 네이티브로 넘기지 않는다.
  - **gge.dll 공유**: 관리 코드의 P/Invoke가 플레이어가 이미 올린 `gge.dll`을 그대로 쓰도록 `Initialize`가 모듈 핸들을 받아 `NativeLibrary.SetDllImportResolver`로 고정한다(스크립트 호스트 폴더에 `gge.dll` 사본이 있어도 두 번째 사본이 올라가지 않게). 빌드는 `script_host`에 `gge.dll`을 복사하지 않고, 플레이어는 종료 직전에 프로세스에 `gge.dll`이 정확히 하나인지 검사한다(`VerifySingleEngineModule`, 어긋나면 실패).
  - **빌드/배치**: `tools\GunGameTools.slnx`(build.cmd)가 `build\bin\script_host\`(호스트 + `GunGame.Scripting.dll` + `GunGame.Interop.dll` + runtimeconfig/deps)와 `build\bin\scripts\GunGame.SampleScripts.dll`을 만든다. ctest의 `gge_player_script_*`는 이 빌드 뒤에 돌아야 한다(build.cmd 순서대로).
- **샘플**: `assets/samples/play.ggs`는 `play.scene.json`을 구운 결과이며 C++ 테스트와 플레이어 ctest가 그대로 읽는다. 어긋나면 `BakedPlaySample_IsUpToDate`가 실패하고, `GGE_WRITE_SAMPLES=<assets/samples>`로 다시 만든다.

## 리소스 수명
- 엔진: `gge_mesh/texture/skeleton/clip_destroy`. 오브젝트가 쓰는 중이면 실패(사용 중인 오브젝트 ID를 오류에 담는다). ID는 재사용되지 않는다. 오브젝트 파괴/교체가 먼저다.
- `SceneSync`는 경로별 캐시에 로드 시점의 파일 수정 시각/크기를 함께 저장한다. `Rebuild`(씬 열기, 구조 변경) 때 오브젝트를 모두 없앤 직후 파일이 바뀌거나 사라진 캐시를 해제하고 다시 읽는다. 메시 캐시가 버려지면 재생 상태(`AnimationPlayer`)도 비운다(해제된 클립 ID를 들고 있으면 엔진 오류). glTF 외부 `.bin` 등 부속 파일은 추적하지 않는다. 속성 변경(Update) 경로는 캐시를 그대로 쓴다.

## 코드 리뷰 후속 처리 (2026-10-30)
서브에이전트가 코드를 읽고 보고한 항목을 하나씩 재현(테스트가 실패하는 것을 확인)한 뒤 고쳤다.

| 항목 | 재현 | 처리 |
|---|---|---|
| glTF 노드 순환/자기 자식/다중 부모로 임포터 무한 루프 | 재현(정지) | 거부 + 조상 탐색 가드 |
| `SceneSync`가 폴더/권한 거부 경로에서 예외 누출 | 재현 | 오류 목록으로 보고 |
| 씬 JSON의 `null` 노드 -> `NullReferenceException` | 재현 | `SceneFormatException` |
| 경로의 NUL 문자 -> `ArgumentException` | 재현 | `SceneFormatException` |
| 계층 약 31단계 이상에서 저장 `JsonException`(한도 64가 무의미) | 재현 | JSON 깊이 한도 조정 + 64단계 초과는 저장/로드 모두 형식 오류 |
| `EngineRenderer`가 짧은 배열을 네이티브로 넘김(과다 읽기) | 재현 | `ArgumentException`(텍스처, 스키닝 메시, 스켈레톤, 클립) |
| glTF 외부 버퍼 URI의 절대 경로/UNC(실제로 SMB 연결 시도) | 재현 | 파일을 열기 전에 거부 |
| glTF 음수 accessor `byteOffset` | 재현 | 거부 |
| glTF 비균등 스케일 법선 오류 | 재현(0.894 대 0.447) | 역전치 행렬 |
| glTF 거울 반전(음의 행렬식) 노드의 감김 뒤집힘 | 재현(삼각형 192개 전부) | 인덱스 순서 교환 |
| `AnimationPlayer` 속도 NaN/무한대, `dt*Speed` 오버플로 -> 시간 NaN 고착 | 재현 | 해당 프레임 진행 무시 |
| 인스펙터 포커스 이동만으로 값이 반올림되어 되써짐 + 변경 알림 | 재현 | 편집한 칸만 반영 |
| 애니메이션 틱(30Hz)마다 상태 표시줄/클립 목록 갱신 | 재현 | `PoseChanged` 분리(다시 그리기만) |
| 깊은 씬 저장 시 `SceneFormatException`이 UI로 누출(직렬화 변경 후 발생) | 재현 | `Save failed`로 표시 |
| `Save` 비원자성 | **재현 불가**(잠긴 파일은 열기 단계에서 실패해 잘림 없음) | 하드닝으로만 적용(임시 파일 + 교체) |
| bufferView 없는 accessor의 거대한 `count` | 과다 개수는 이미 `GltfException`(overflow 변환). OOM 경로는 **수정 전 재현 안 함**(대용량 할당 위험) | 상한(1600만) 추가, 수정 후 테스트 |
| 경로 `C:a:b`의 `NotSupportedException` | **재현 불가**(예외 없음) | 조치 없음 |
| 클립 시간 검증 누락 / `duration`이 최댓값이 아님 | 해당 없음(네이티브가 거부, `duration`은 이미 채널 간 최댓값) | 조치 없음 |
| 뷰포트 stride 불일치 | 해당 없음(엔진이 `Width*4`로 촘촘히 채움) | 조치 없음 |
| 엔진/IO 예외가 `Rebuild`/속성 핸들러로 새는 일반 경우, `DispatcherUnhandledException` 부재 | **재현 불가**(현실적인 유발 입력을 못 찾음) | 조치 없음(추측성 방어 코드 미추가) |
- 알려진 잔여: `LoadGltf`가 중간에 실패하면(예: 클립 생성 거부) 이미 만든 메시/스켈레톤이 엔진에 남는다(누수, 기능 영향 없음).

## 에셋/씬 포맷
- **메시**: `.obj`(원본) → `.ggm`(엔진 바이너리, `GGM1` + 정점 수 + 인덱스 수 + float[8]*N + uint32*M). 로더는 크기·인덱스 범위를 검증한다.
- **스키닝 메시/애니메이션 원본**: `.glb`/`.gltf`(Blender 등에서 내보내기). 에디터가 로드할 때 임포트해 엔진 리소스로 만들고, 독립 플레이어용으로는 Bake가 `.ggs`에 합친다. 샘플은 `GGE_WRITE_SAMPLES=<폴더>`로 `SampleAssetTests`를 실행해 다시 만든다(`play.ggs` 포함).
- **텍스처**: PNG/BMP/JPEG를 WIC로 읽어 RGBA8로 사용. 점 샘플링, 반복(wrap).
- **씬**: `*.scene.json`(버전 1). 메시/텍스처 경로는 씬 파일 기준 상대 경로, 회전은 라디안(UI는 도). 선택 섹션: `gameplay`, `lighting`(없으면 이전 파일과 같다).
- **구운 씬**: `*.ggs`(위 "구운 씬과 독립 플레이어").

## 테스트 하네스
- **테스트가 실제로 결함을 잡는지**는 별도로 측정한다(뮤테이션/커버리지). 결과, 약점 유형, 재현 방법은 `doc/03_Test_Quality_Report.md`, 스크립트는 `tools/mutation/`.
- **C++**: `engine/tests/engine_tests.cpp`. 외부 프레임워크 없이 C API 경계를 검증. 골든 이미지는 `engine/tests/golden/*.ppm`, `GGE_UPDATE_GOLDEN=1`로 재생성(재생성 후에는 반드시 이미지를 눈으로 확인).
- **C#**: `tools/GunGame.Interop.Tests` (xUnit). 실제 `gge.dll`을 WARP로 호출.
- **WPF 화면**: `GunGameEditor.exe --selftest <scene.json|obj> <png>`. OS 화면 캡처 없이 앱이 그린 비트맵과 창 전체(`.window.png`)를 직접 저장.
- 기본 테스트는 GPU 대신 WARP(소프트웨어 어댑터)를 사용해 결과를 안정화한다. `build.cmd test-gpu`(환경 변수 `GGE_FORCE_DEVICE=hardware|warp`가 호출자의 선택을 덮어씀)는 같은 테스트를 하드웨어 GPU로 돌리며, 이때 골든 비교만 골든 기준 경계 픽셀 차이를 전체의 1%까지 허용한다.

## 성능 측정
- `build\bin\engine_bench.exe` [--hw] (ctest 미등록, 수동 실행): 64x48에서 시나리오별 프레임당 ms(기본 WARP, `--hw`는 하드웨어 GPU). 해상도를 작게 해 래스터화보다 CPU 쪽 비용이 드러나게 한다.
- 2026-10-30 기준선(WARP): 평면 큐브 1000개 4.2ms, 깊이 20 계층 2000개 9.4ms -> 8.4ms(월드 행렬 프레임 캐시 후), 스키닝 50개x본 32 0.37ms.
- 엔진 자체의 CPU 로직(행렬/상수 준비)은 평면 1000개에서 0.07ms로 프레임의 약 2%다. 나머지는 객체마다 D3D 호출(상수 버퍼 갱신 + DrawIndexed) 비용이라, 더 줄이려면 배칭/인스턴싱 같은 구조 변경이 필요하다. 하드웨어 GPU(2026-10-31, 기본 어댑터): 평면 1000개 0.76ms, 계층 100x20 1.03ms, 스키닝 0.37ms로 이 규모에선 급하지 않다.

## 빌드
`build.cmd` (빌드), `build.cmd test` (빌드 + 전체 테스트). 요구: Visual Studio/Build Tools(C++ 워크로드), CMake, .NET SDK 10(Ninja 불필요). `build.cmd test`는 엔진 테스트 + 플레이어 ctest 5개 + C# 테스트 + UI 입력 테스트 + 뷰어 selftest를 모두 돌린다. `build.cmd test-gpu`는 같은 전체를 하드웨어 GPU로 돌린다.
